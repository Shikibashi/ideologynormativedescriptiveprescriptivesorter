# Implementation Plan — Ideology Layer Sorter

## Strategy Decision

### Candidate A — React + TypeScript + Vite, client-only

Use a small typed domain core, immutable content modules, one React composition root, and pure scoring/share functions. Ship as a static site with Vitest and Playwright. This best matches the empty workspace, the need for interactive progress, and the no-remote-storage boundary.

### Candidate B — Vanilla TypeScript + Web Components

Use native custom elements and a small state machine with no React dependency. This reduces runtime dependencies, but it makes the layered result composition and test ergonomics less direct for this first build. It remains a viable later simplification if the UI stabilizes.

### Candidate C — Full-stack app with API and database

Add a server for answer persistence, content management, and future cohort analysis. That would create privacy, consent, authentication, deployment, and data-retention obligations that the brief does not ask for. It is intentionally outside the MVP.

### Qualitative decision record

| Criterion | Candidate A | Candidate B | Candidate C |
|---|---|---|---|
| Brief fit | Strong: interactive layered flow and inspectable local data. | Strong: same behavior is possible. | Weak: adds an unrequested collection boundary. |
| Domain fit | Strong: typed data and pure domain functions are natural. | Acceptable: requires more custom UI plumbing. | Deferred: would need a separate consent/data governance design. |
| Risk and complexity | Low: small dependency surface and no server. | Low-to-medium: browser semantics move into custom code. | High: privacy and operations become product features. |
| Reversibility | Strong: data/scoring contracts can be reused by another shell. | Strong: content/scoring remain portable. | Low: server contracts become a larger migration boundary. |
| Effort | Appropriate for a one-turn MVP. | Appropriate but slower to polish and test. | Disproportionate to the stated goal. |

**Selected:** Candidate A. **Grafted idea:** retain Candidate B's domain isolation by keeping scoring, dataset validation, and share encoding framework-independent. Candidate C is deferred through the explicit scope gate.

The research workbench derives its target inventory from the ontology and secondary registry rather than duplicating the list in UI code. It distinguishes dedicated scored coverage, partial dedicated coverage, scored-indirect coverage, contextual-only anchors, catalog-only entries, and registry-only context. A candidate must state why the target is substantively distinct, use one respondent-facing claim, map to an existing layer/facet, cite ideology-research sources, and remain labeled `research_candidate`. Candidate drafts are an authoring aid only; they cannot add effects, alter anchors, change thresholds, or enter the live quiz. Before any future production promotion, the candidate must pass neighbor-distinctness review, applicable cross-cultural/jurisdictional review, and later empirical validation.

Anchors cover 50 editorial vectors. Forty-five canonical-placement anchors enter the production neighbor set; five contextual bridge anchors remain visible for provenance and interpretation but are intentionally excluded from production scoring. The family cardinalities are intentionally not treated as equal evidence; family balancing is a display constraint, not a claim that the taxonomy is balanced. Every anchor includes a short summary, an authorial note, source posture, family, and content version.

## Scoring policy

- Directional values: `-2, -1, 0, +1, +2`.
- `Mixed / depends`: answered midpoint `0`, counted in coverage, shown separately in the method note.
- `No view yet`: missing, excluded from coverage numerator and facet denominators.
- Coverage threshold: `answered / layer total >= 0.5`; at exactly 0.5 the layer is eligible.
- Profile aggregation: signed effect times answer, normalized by observed absolute effect magnitude per facet.
- Anchor distance: weighted squared distance over observed facets only.
- Fit display: normalized internal fit, rounded only at the presentation boundary.
- Neighbor selection: one nearest per family, then fill remaining slots; stable tie order by family and ID.
- Tensions: rule-based descriptive text across layer profiles; no consistency score.
