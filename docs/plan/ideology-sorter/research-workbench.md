# Research Workbench Contract

## Purpose

The research workbench is a local authoring surface for finding measurement gaps and drafting candidate items. It is not a respondent-facing classifier, a publishing system, or a psychometric calibration tool. The production sorter remains the only source of live scoring behavior.

The workbench follows the supplied ontology audit and measurement specification. Taxonomic ancestry, contextual registry membership, cross-tree relations, measurement coverage, and candidate-item review are separate concepts. A parentless hybrid or a contextual registry entry must not be forced into a canonical breadcrumb merely to make the UI look complete.

## Derived target inventory

`buildResearchTargets()` derives one target record for every `ideologyNode` and `ideologyRegistry` entry in the current dataset. The current inventory is 127 targets: 124 ontology nodes and 3 registry entries. The UI does not duplicate that list. The completed coverage continuation adds a separate 1,524-item, effect-free research-candidate pool for all 127 targets; those records are displayed here for authoring review but are not respondent-facing questions.

Each target exposes:

- stable ID, label, aliases, level, placement, and summary;
- canonical path only when the node has taxonomic ancestry;
- anchor ID and per-layer question counts when scored;
- explicit target-tagged question IDs and separately labeled source-linked context IDs;
- existing construct IDs and facet-axis proxies;
- typed neighbor IDs/labels and relation metadata;
- source references and a derived measurement state.

The measurement states are intentionally not synonyms:

| State | Meaning |
|---|---|
| `dedicated-scored` | A scored node has at least the research triage threshold of four explicitly target-tagged items in every layer. |
| `partial-dedicated` | A scored node has some, but not all, layer coverage from explicitly target-tagged items. |
| `scored-indirect` | A scored node exists, but no production item explicitly claims to target it. |
| `contextual-only` | A contextual anchor remains visible for provenance and interpretation, but its broad or bridge meaning is excluded from production neighbor scoring. |
| `catalog-only` | An ontology node is cataloged without a scored anchor. |
| `registry-only` | A contextual, historical, associated, or contested registry entry is kept outside the canonical scored graph. |

The four-item threshold is an authoring triage rule. It is not a reliability threshold, an information-gain estimate, or evidence that a branch is scientifically identifiable.

## Candidate record

A candidate is a `ResearchQuestionCandidate`, not a `Question`. It must contain:

1. a target ID and target-specific substantive-distinctness justification;
2. one respondent-facing claim in `exactWording`;
3. layer, domain, construct, and an existing facet-axis mapping;
4. theory context (`ideal`, `nonideal`, or `mixed`);
5. item function, qualitative expected direction, and named neighboring branches it should help distinguish;
6. an academic rationale and one or more source IDs, including at least one `ideology-research` source;
7. why the item is needed and what same-answer/different-reason risk remains;
8. ambiguity, social-desirability, jurisdiction/cultural, and temporal-stability notes;
9. the recommended five-point directional response format, confidence, `review_status: research_candidate`, and a promotion-review record whose checks and evidence fields begin pending.

The editor starts with a blank candidate. It does not generate effects, assign an anchor, alter the manifest, or infer a psychometric property. A warning about a target name in wording, a conjunction, or absent neighbor differentiation is non-blocking editorial feedback; validation still requires the blocking fields above.

## Review and activation boundary

Saving a draft keeps it in the current browser session. Copying exports the review record as JSON. Neither operation changes the production bank, answer map, effects, anchors, thresholds, content version, share envelope, or result labels. There is deliberately no “publish,” “activate,” or “score this item” control.

Before any candidate could be promoted into the production bank in a later change, the promotion gate must establish at least:

- a substantive neighbor-distinctness review showing why the candidate separates the target from its named neighbors;
- one-claim wording and a response scale that matches the construct;
- source-to-construct traceability without copying source wording or code;
- documented wording and construct-review evidence;
- cross-cultural, jurisdictional, translation, and temporal review where applicable, or an explicit not-applicable rationale;
- later empirical validation recorded as passed;
- explicit approval for any production data or scoring change.

The current implementation records these as pending review fields, not as completed evidence. `validateResearchPromotion()` is the future promotion check; the current UI has no promotion path and every saved record remains `research_candidate`. The academic and survey-methodology records in `src/data.ts` support construct framing and item-writing discipline; they do not validate this application’s editorial anchors. In particular, [Treier and Hillygus](https://doi.org/10.1093/poq/nfp067) and [Bakker, Jolly, and Polk](https://doi.org/10.1177/1465116512436995) are used for multidimensionality context, while [AAPOR best practices](https://aapor.org/standards-and-ethics/best-practices/) and the [AAPOR/WAPOR comparative survey-quality report](https://aapor.org/wp-content/uploads/2022/11/AAPOR-WAPOR-Task-Force-Report-on-Quality-in-Comparative-Surveys_Full-Report.pdf) inform question design, cross-context interpretation, and transparent reporting.
